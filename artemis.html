Enhancement narrative

Artifact and purpose

My artifact is the Artemis Financial project that I created during CS 305, before this capstone course. The original Java application uses Spring Boot to return a SHA-256 checksum for a supplied value. It also includes HTTPS configuration and a dependency-checking tool. I selected it because I could build on its security purpose while showing more of what I know about algorithms and data structures. The portfolio includes the original source and a separate enhanced version, with private key material omitted from the public copy.

What the enhancement adds

The main addition is a Merkle tree. It hashes each record, combines neighboring hashes, and repeats that process until one tree root remains. Node objects hold the hashes and links to child nodes. Recursive methods build the tree and follow the path to a selected record. The program can return the root, create a membership proof, and check that proof against a root the verifier already trusts. The original checksum endpoint is still available.

A membership proof contains the sibling hashes needed to connect one record to the root. This lets the program check that record without receiving the entire collection again. Different prefixes distinguish record hashes from combined hashes, following a design principle described in RFC 9162 (Laurie et al., 2021). This project uses its own documented format, rather than implementing the full RFC. If a level has an odd number of nodes, it duplicates the final hash. The returned root also includes the original record count so that duplicating a final record does not make two different-sized collections appear identical.

The cost comparison is an important part of the enhancement. Building the tree requires work proportional to the total input bytes and number of records. Once it exists, creating a proof follows one path through the tree. Verification reads the selected value and that path, which grows logarithmically with the number of records. For 4,096 records, the demo reports 8,192 hash calls to build the tree and 14 to verify one value. These are operation counts, not timing measurements. The web proof endpoint still rebuilds the tree from the supplied collection, so that whole request has a linear construction cost.

It supports outcome 4 through Java implementation, reusable classes, and automated checks. Expected roots generated separately with Python were also checked against the Java results. The full Maven build could not run because the test environment could not reach the dependency server. The Spring Boot endpoints, HTTPS setup, and dependency scan still need local verification. I am keeping those results separate from the successful core checks.

Reflection and remaining work

The main lesson is that an algorithm needs clear rules for unusual inputs, not just the usual case. An odd final node seems like a small detail, but it affects the root and the proof. Including the record count addresses an ambiguity caused by duplication. Another important lesson is that a matching hash does not prove that data is trustworthy by itself. The expected root must come from a trusted source. The tree also uses more memory than one checksum, so its value is in checking individual records after construction. My next steps are to run the full application locally, review the test results, and address any issues found during testing.

# Algorithm and complexity

## Deterministic rules

This is a custom classroom SHA-256 Merkle scheme, not a Certificate Transparency protocol implementation. It uses different prefixes for leaves and internal nodes, a practice described in RFC 9162 section 2.1.1. The odd-node rule and count commitment below are specific to this project.

- Values are ordered, exact UTF-8 strings. No trimming or Unicode normalization changes the records.
- Leaf: SHA256(0x00 || UTF8(value)).
- Internal node: SHA256(0x01 || leftHash || rightHash), joining raw 32-byte hashes.
- At every odd-width level, duplicate the final hash to create its parent. Node references are shared rather than copying the subtree.
- Returned root: SHA256(0x02 || countAsFourBigEndianBytes || internalTreeRoot).
- Empty collection: SHA256(0x02 || four zero bytes), with no internal hash and no valid membership proof.
- A one-value collection has one leaf, a root commitment, and an empty sibling list.

The count commitment matters: without it, duplicating a final value can make `[A,B,C]` and `[A,B,C,C]` share the same tree hash. Including the count distinguishes the collections. Hash domain prefixes distinguish records from combined child hashes. Proof verification checks both metadata and hashes.

## Construction and proof algorithms

1. Validate limits and hash each record into an immutable leaf node.
2. `buildLevel` pairs neighboring nodes, creates parents, and recursively calls itself on the smaller parent list until one node remains.
3. Each node stores its hash, two children, and the original leaf-index range. `collect` follows the target index through one child at each level and adds the sibling hash as recursion returns.
4. `verify` hashes the supplied record, derives left/right position from index parity, and combines sibling hashes until it reaches the internal root. At an odd duplicated position it also checks that the sibling equals the current hash.
5. Verification requires exactly the expected path length, valid index/count, and 32-byte hexadecimal hashes. It wraps the result with the count commitment and compares it to the separately supplied trusted root.

## Cost model

Let n be the number of records, B their total UTF-8 byte length, and L the selected record's byte length. SHA-256 must read all bytes, so variable-length inputs must be included in the analysis.

| Operation | Time | Additional/storage cost |
| --- | --- | --- |
| Build complete tree | O(B + n) | O(n) nodes/hashes plus transient per-value encoding |
| Read cached root | O(1) | O(1) |
| Produce proof from cached tree | O(log n) for n > 1 | O(log n) sibling hashes and recursion |
| Verify one value | O(L + log n) | O(1) working hash state beyond the supplied O(log n) proof |
| API request that builds and returns proof | O(B + n) | O(n), including the rebuilt tree |
| Rebuild after a changed record | O(B + n) | O(n); incremental updates are not implemented |

Construction recursion depth is O(log n). Validation and leaf encoding add work proportional to input bytes. Stored hashes are fixed at 32 bytes. The input strings are supplied by the caller and are not retained by the tree.

For n=2^k: n leaf hashes + (n-1) internal hashes + one count commitment = 2n build hashes. A valid proof contains k siblings and uses k+2 hashes (leaf + siblings + commitment). The demo records exact hash-operation counts, not wall-clock speed. SHA-256 calls on records of different byte lengths are not equal-cost timing measurements.

The tree uses more memory than a single checksum but permits verification of one record without sending the full collection after a root and proof exist. It preserves ordering; this is not a sorted tree, a signature, or encryption. A trusted root is essential because an attacker able to replace both data and the trusted root can create a self-consistent replacement tree.

# Artemis Financial Merkle Tree Enhancement

This CS 499 Milestone Three version extends the CS 305 SHA-256 checksum project with ordered record verification. The original `/hash?data=...` endpoint remains. MerkleTree is plain Java; the web controllers call it without duplicating its algorithm.

## Open it on Windows

1. Extract the submission ZIP into a new folder, for example `G:\CS499\MilestoneThree`.
2. Open IntelliJ IDEA, choose **Open**, and select this `Enhanced_ArtemisFinancial` folder containing `pom.xml`. In VS Code, choose **File > Open Folder** and select the same folder.
3. Use **JDK 17 or newer**. Run `java -version` in the terminal to check. Set the IDE's project JDK and Maven runner JDK to the same installation. An Android Studio bundled JDK can also run the core script if its `bin` folder is on PATH.
4. Open the terminal in this folder. Run the core test and demo without downloading Maven dependencies:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-core-checks.ps1
```

The policy option applies only to this script process. It does not change the machine's permanent policy. Expected: `PASS: 16687 core checks`, then `Original value verifies: true` and `Changed value verifies: false`.

## Run the complete project

With an internet connection for Maven dependencies:

```powershell
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
```

First use downloads Maven and dependencies. The app binds to **127.0.0.1:8080**, local computer only. This HTTP mode is for the classroom demo. Press Ctrl+C to stop it.

Open `http://127.0.0.1:8080/hash?data=abc` to see the existing checksum feature. Open a second PowerShell terminal and run:

```powershell
$body = @{ values = @('Invoice A:100','Invoice B:200','Invoice C:300'); leafIndex = 1 } | ConvertTo-Json
$result = Invoke-RestMethod http://127.0.0.1:8080/merkle/proof -Method Post -ContentType 'application/json' -Body $body
$result | ConvertTo-Json -Depth 6
$trustedRoot = $result.root
$check = @{ value = 'Invoice B:200'; proof = $result.proof; expectedRoot = $trustedRoot }
Invoke-RestMethod http://127.0.0.1:8080/merkle/verify -Method Post -ContentType 'application/json' -Body ($check | ConvertTo-Json -Depth 6)
$check.value = 'Invoice B:999'
Invoke-RestMethod http://127.0.0.1:8080/merkle/verify -Method Post -ContentType 'application/json' -Body ($check | ConvertTo-Json -Depth 6)
```

The first verification should return `valid: true`, the changed record `valid: false`. Saving the root from this locally built sample demonstrates the flow. In a real system the verifier must obtain an authentic root independently of an untrusted proof provider.

## API

`POST /merkle/root`: `{"values":["A","B","C"]}` returns root, leafCount, and buildHashCount.

`POST /merkle/proof`: `{"values":["A","B","C"],"leafIndex":1}` returns root and proof. Indexes start at zero. A proof has leafIndex, leafCount, and sibling hashes in leaf-to-root order.

`POST /merkle/verify`: `{"value":"B","expectedRoot":"64 hexadecimal characters","proof":{"leafIndex":1,"leafCount":3,"siblings":["...","..."]}}` returns a validity Boolean. Missing required fields/malformed JSON yields HTTP 400; a well-formed but invalid proof yields false.

The API is stateless. The proof endpoint rebuilds from supplied values each time (linear total work); only `proof(index)` on an already built tree and verification are logarithmic. No database, user authentication, or durable tree storage is provided.

## HTTPS configuration

The enhanced copy removes the old private keystores and hard-coded password. Private keystores are also omitted from the public original copy. Generate a new development keystore outside the project using your JDK:

```powershell
keytool -genkeypair -alias artemis -keyalg RSA -keysize 3072 -storetype PKCS12 -keystore "$env:USERPROFILE\artemis-dev.p12" -validity 365 -dname "CN=localhost" -ext "SAN=dns:localhost,ip:127.0.0.1"
$env:ARTEMIS_KEYSTORE = "file:" + ($env:USERPROFILE -replace '\\','/') + '/artemis-dev.p12'
$secret = Read-Host 'Keystore password' -AsSecureString
$env:ARTEMIS_KEYSTORE_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
.\mvnw.cmd spring-boot:run '-Dspring-boot.run.profiles=tls'
```

Use `https://localhost:8443/hash?data=abc`. A self-signed development certificate is not automatically trusted by your browser. HTTPS startup and certificate trust still need local verification. Remove the temporary password variable after stopping: `Remove-Item Env:ARTEMIS_KEYSTORE_PASSWORD`. Do not commit the keystore or password.

## Dependency audit and limits

```powershell
.\mvnw.cmd -Psecurity-audit verify
```

The explicit audit profile uses Dependency-Check 13.0.0 with a CVSS threshold of 7. An optional NVD API key is read from `NVD_API_KEY`, not stored in the POM. The scan needs internet access and may take time; it has not been run here. The baseline's old suppression file is not carried forward.

Spring Boot is pinned to 3.5.16 as an intermediate update from the old 2.2.4 baseline. Its open-source support has ended; this is a local coursework build, not a production deployment. Moving to a supported 4.x generation and rerunning compatibility/security tests remains release work. No claim of vulnerability-free dependencies is made.

Input limits: at most 4096 leaves, 4096 UTF-8 bytes per value, 1 MiB total record data. Empty strings are allowed, nulls and malformed Unicode are rejected. Bounds apply after JSON deserialization; an exposed service would also need transport body-size limits, authentication, and rate limiting. Hashes prove consistency with a trusted root, not identity, authorization, truth of a record, or confidentiality. Repeated equal values can have proofs at multiple valid positions.
