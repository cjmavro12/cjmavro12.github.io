Professional direction

I am CJ Mavrogeorge, a U.S. Army veteran and a Business Class Field Technician at Spectrum working toward my B.S. in Computer Science at Southern New Hampshire University. My goal is to move into network or software engineering. My technical work and coursework have helped me connect practical troubleshooting with the software that stores information, supports users, and keeps services dependable. This portfolio brings together three projects that show how I have grown from getting a program to work to explaining its design, evaluating tradeoffs, and improving its reliability.

Growth through the program

The capstone gave me a reason to revisit work from CS 360, CS 305, and CS 340. Looking at those projects together showed me that a working interface is only one part of a useful system. I also need to consider how responsibilities are separated, how an algorithm handles unusual inputs, how database operations behave, and what evidence supports a claim. The enhanced artifacts show that growth in three different environments: Android, a Java web application, and a Python dashboard backed by MongoDB.

Communication and collaboration

My code review explains the original projects and planned improvements for a technical audience. The project narratives explain why I selected each artifact, what changed, and what I learned. The setup guides and test records make the work easier for another developer to understand and continue. These are individual course projects. The documentation gives another person a starting point for reviewing the code, running the tests, and discussing changes. It also helps me explain what works and what still needs testing. Working through these projects taught me to give specific reasons for a change and keep clear notes so someone else can follow my decisions.

Software design and security

The Weight App helped me understand why screen code should not handle every responsibility. ViewModels, a repository, validation, and a separate notification component make the design easier to follow. Moving database operations and password hashing off the main thread also addresses responsiveness. Salted password hashes improve password storage, but the migration must preserve existing accounts and records. That tradeoff taught me to consider both protection and continuity for users. Security also appears in the database artifact through validated inputs and single-record updates, and in Artemis through integrity verification and limits on input.

Algorithms and database decisions

The Artemis enhancement demonstrates tree construction, recursion, and membership proofs. For a 4,096-record example, the implementation reports 8,192 hash calls to build the tree and 14 to verify a value. Those counts describe algorithmic work, not elapsed time. Building the tree has a cost, and the web proof request still rebuilds it. The database enhancement makes a different tradeoff: filtering, counting, and grouping run in MongoDB, while the dashboard receives a bounded page. The index and explain-plan script provide a way to investigate performance, but the index has not been proven faster on a live server.

Evidence and next steps

The Java core passed 16,687 checks, and the database application passed 13 automated tests using an in-memory substitute. My manual checks confirmed the basic Android app functions. These results have different scopes: they do not establish a successful full Maven build, Android migration test, or live MongoDB deployment. The project pages identify the remaining verification. Keeping those limits visible is part of communicating responsibly about software. Together, the artifacts provide evidence of communication, algorithmic problem-solving, development techniques, and a security mindset, while the review materials show how I make technical work understandable to others. I want to carry that combination of practical troubleshooting and careful software development into my next role.
